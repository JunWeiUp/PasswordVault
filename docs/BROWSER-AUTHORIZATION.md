# Browser account access and Mac startup unlock

Browser 2.2.9 and Mac 2.0.12 extend the previous save-only capability with explicit current-site reads/fills and optional Mac startup unlock. The native helper remains on demand; no daemon, browser WASM vault or background Mac window is added.

## Setup and everyday behavior

In the extension's **连接 Mac** mode, enter the existing Mac vault master password and choose **确认授权**. The form explicitly authorizes current-site account lookup, password reveal/fill and saving. **打开 Mac 时自动解锁** is a visible checkbox, initially checked, that can be unchecked before confirming. Existing save-only grants are never silently widened: choose **启用账号显示与自动解锁** and verify the master password again.

After authorization, the popup shows the current website's matching accounts even with the Mac main application quit. The toolbar badge shows the account count (0 when none, 99+ above 99). A pending login confirmation retains the existing + priority. Exact-hostname matching across ports, subdomain isolation and HTTPS-to-HTTP protection remain unchanged. Additional accounts retain their own account IDs.

Passwords are masked until **显示密码** is clicked. The worker verifies trusted extension UI, browser-owned tab origin and account membership, and checks navigation again after retrieval. Revealed text is concealed after 30 seconds, on blur/visibility changes, account/origin changes or another busy action. Late responses after concealment or navigation are discarded. Fill remains explicit and never submits the website form.

The popup's **锁定** and browser idle/OS-lock events pause browser reads in session storage; background saving remains available. Reverify the password to resume reads. Browser session state does not survive a full browser restart; the explicitly persistent native authorization does. Revoking the capability or changing the master password invalidates its future uses.

## Mac startup unlock

With the checkbox enabled, a cold Mac app launch attempts one automatic unlock. It does not run again on status polling or reopening a window in the same process. Manual/idle/system lock invalidates an in-flight startup challenge. Subsequent cold launches still follow the persistent startup option; disable it if every launch should require a password.

The most recently enabled plugin authorization supplies the startup source for a vault. Other browsers' read/save grants remain independent. **关闭 Mac 自动解锁** removes the startup source while preserving this plugin's account access. **撤销此插件授权**, Mac Settings → Browser → **撤销全部浏览器资料库授权**, or a master-password change invalidates the corresponding future unlock path.

Missing, invalid or inaccessible authorization falls back to the normal master-password screen. No password is persisted. Local ad-hoc helper updates can invalidate Keychain ACL access; reauthorization is then necessary. No attempt is made to extract or migrate an existing private grant through an untrusted process.

## Native trust and data flow

The existing helper-owned login-Keychain entry stores a versioned authorization envelope containing the native grant and explicit read/startup scopes. Old raw 64-byte grants decode as save-only. A separate helper-protected Keychain index identifies the selected startup owner. Its account is scoped to the helper code identity so reauthorization after an ad-hoc update creates a fresh index instead of trying to bypass an old ACL. A helper update can therefore require explicitly enabling startup unlock again. The browser receives neither root material nor a saved master password.

For website reads, the helper checks the stored read scope and permits only matches/fill. It uses the desktop's serialized session when available; otherwise it briefly owns the same exclusive vault lock. Temporary reads relock a previously locked core before returning and do not unlock the desktop UI. Website results return only scoped metadata or the explicitly selected credential, never a general document/export interface.

For startup unlock, the Mac app launches its helper in a dedicated desktop mode. The helper verifies the parent's code signature against the bundled desktop executable. It sends the grant over the existing signed-peer socket with a one-use, in-memory startup challenge generated by that AppStore. Browser-mode requests cannot invoke this operation or supply a native grant. No root material is emitted on helper stdout. Rust revalidates the current password-header/revocation fingerprint immediately before unlocking.

These are native-code scope restrictions around root-bearing Keychain material, not cryptographic write-only/read-only keys. A compromised helper, OS or its Keychain grant can compromise the vault. Login-Keychain authorization is not Touch ID or an independent security audit. See the [security model](SECURITY_MODEL.md).

## Evidence and remaining gates

- 31 Rust tests: native read scope, foreign-origin denial, locked-state preservation, startup unlock, password-change/revocation rejection, append retry/rollback and existing core cases.
- 69 Swift tests: real helper/Keychain startup unlock, save-only denial, wrong/revoked authorization, manual-lock race cancellation, challenge replay rejection and unchanged UI lock during browser reads, plus existing Mac regressions.
- 37 browser tests: current-site account list and numeric badge with desktop closed, trusted-UI reveal, changed-origin denial, paused-read enforcement, explicit scope flags and existing save/fill behavior.
- Real 380×600 DOM fixtures: confirmation (8), manual entry (2), offline saving (3), legacy edit/fill navigation (5), new authorization (4), account reveal/concealment (4). These use fictional bridge data. The helper tests separately use disposable vaults.

Run the core/macos/browser modes of tool/check_native.sh, the Debug Swift test scheme, and the exported popup scenarios. Full installed Chrome/Edge credential delivery, macOS 13/Intel, physical login-Keychain lock/unlock and production signing/upgrades remain separate acceptance gates.
